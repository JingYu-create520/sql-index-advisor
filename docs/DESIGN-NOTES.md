# 设计说明

这份文档只回答"为什么是这个形状"，不记录进度，也不记录待办。每条规则怎么判定写在 [rules.md](rules.md)。

编号 D1~D11 被源码注释直接引用（例如 `src/rules/sia001.ts` 引 D1），要改编号得同步改注释。

## 十一个决定

| # | 决定 | 为什么 |
|---|---|---|
| D1 | 复合索引列顺序是**等值 → 排序/GROUP BY → 范围** | 索引一旦在某一列上做范围扫描，它后面的列既不能继续用于等值定位，也不能用于消除排序。把范围列排在排序列前面，等于亲手制造一次 `Using filesort`。这一条最初写的是"等值 → 范围 → 排序"，那是错的，而且错得很典型 |
| D2 | 慢日志按 **SQL 指纹**聚合，不按事件逐条报 | 真实日志里同一个 pattern 一天几百条。逐条报告会淹没排序，看不出这周该先修哪一条 |
| D3 | `schema.json` 由用户自己导，工具**不连数据库** | 一条纯 `information_schema` 查询就够（`examples/schema-dump.sql`）。不连库才可能进沙箱化的 CI job，也省掉密码这件事 |
| D4 | SIA006 只对**字面量 offset** 生效 | `LIMIT #{offset}, #{size}` 静态无解，硬判必然误报。漏一条比报错一条便宜 |
| D5 | 输入依赖拆成 `needsSchema` 和 `needsMetrics` 两个标记 | 这是两种不同的缺失。混成"需要 schema"就没法解释一条规则为什么沉默 |
| D6 | 退出码 `0` 没有 · `1` 达到 `--fail-on`（默认 error）· `2` 运行错误 | 首次接一个老仓库就把构建判红，只会让人卸载工具，不会让人去修 SQL |
| D7 | 前缀索引阈值按**字节**算，并且有 `--mysql-version` | `VARCHAR > 255` 那条流传很广的经验来自 767 字节 + utf8mb3。utf8mb4 一个字符 4 字节，8.0 DYNAMIC 的下限是 3072 字节，真正该问的是这列占多少字节 |
| D8 | 解析器从第一条提交起就保留**行号** | 没有行号，PR 行级评论做不出来，事后补等于重写解析层 |
| D9 | CLI 和 MCP 先做，Skill 和 Action 后做 | 自研 SQL 解析器是真实的消耗点，先把只有两条路能验证的东西验证掉 |
| D10 | 不发 npm，只走 GitHub 直装；构建产物提交进仓库 | 发包要多一个账号和长期维护面。原以为靠 `prepare` 现场构建就够，结果 0.1.5 在 GitHub 的干净 runner 上装失败（prepare 里 `tsup: not found`，exit 127），是仓库自己的 Action 在 PR 上抓到的。现在 `dist/` 入库，`prepare` 只在有工具链时重建，CI 比对 `dist/` 与 `src/` 不同步就红。代价是 MCP 官方 registry 这类要求 npm 包名的收录渠道走不通，另外产物得跟着源码一起提交 |
| D11 | LLM 只能是文案层 | 只要它能增删或者重排建议，结论就不可复现，而这个工具的立论就是可复现。有一条测试断言：开不开 `--llm`，findings 逐字节相同 |

## 明确不做

直连数据库跑 `EXPLAIN`（`--explain` 排在 v2）、PostgreSQL 与其他方言、Web UI、索引成本模型（写放大和空间估算）、自动建索引。最后一项是红线：工具只生成 SQL，执行的人是人。

## 发一个版本要做的四步

没有发包自动化，全是手工，少一步就有一个对外承诺是坏的：

1. 改 `package.json` 的版本号。`sia --version` 和 MCP 的 `serverInfo` 都从它读（`src/version.ts`），不要再往源码里写字面量：0.1.1 那次就是两处字面量没跟上，版本号自己撒了谎。
2. `CHANGELOG.md` 里把这一版写清：修了什么、用户能看见的行为差异是什么。
3. 打 `vX.Y.Z` 标签并推，然后**把浮动标签 `v0` 移到这个新提交再推一次**。README 和示例工作流里写的都是 `uses: …@v0`，`v0` 不存在时那两行就是坏的（0.1.2 修的就是这个）。
4. 建 GitHub Release，正文用 CHANGELOG 那一节。

## 已知的能力边界

- **看不到数据。** 只有 SQL 和表结构，所以"这列区分度低"只能靠列名和声明类型猜。用 `information_schema` 的统计信息替代猜测这条路，实测过并否决了，数字在 [rules.md](rules.md) 的 SIA001 一节。
- **解析器是手写的，范围是写死的。** 超出支持子集的语句会被跳过并给一条 `info`，不会猜一个建议出来。真正的风险不是漏报，是"跳过"被读成"通过"，所以报告底部必须列出未参与判定的规则。
- **建议的新鲜度取决于 `schema.json`。** 导出的表结构过期，SIA002 / 003 / 005 / 007 就会拿旧索引说话。工具不联网，也就无从知道自己看的是一份几天前的导出。
